# Design: relay transport (`agentd-relay`)

Status: **accepted and implemented** (2026-11-18): decisions in [[plans/relay_plan]] (§12 options taken as
recommended), normative protocol v1 in `docs/plans/agentd/relay_plan.md`.
Related: [[design/cross-host-relay]] (mail bridged by a client; a different feature, see §10),
[[design/api/security-remote]] (gateway tokens and pairing, frozen), [[architecture/herdrup-analysis]]
(herdrup guests), `herdr-movil/alma-desktop.md` §3 (Alma's e2e relay), `herdr-movil/moshi.md` §6-7.

## 1. Goal

Clients (agentd-desktop today, a mobile app later) reach a host either:

- **over SSH** (today: `direct-streamlocal` to the daemon socket, caller = `human:<ssh user>`), or
- **through a relay**: a small public rendezvous server, `agentd-relay`, that both the daemon and the
  client dial **out** to. No inbound port on the host, no VPN, works behind NAT/CGNAT.

The relay is **blind and untrusted**: it routes encrypted bytes between a client and a host, it never
holds a key that can read or forge traffic, and it decides nothing about permissions. Permissions are
decided by the host daemon, per paired device.

## 2. What other clients do

| Product | Rendezvous | E2E | Pairing / invite | Permissions |
|---|---|---|---|---|
| Alma | `relay.alma.now` (Cloudflare Worker) + direct LAN route | ECDH P-256 + HKDF(code) + AES-GCM per direction, mutual confirm MACs | QR/link `alma://connect?u=<relay>&k=<32-byte code>`; route id = HKDF(code); regenerating the code revokes (`pairing-replaced`) | none: a paired phone is the owner |
| Moshi | cloud hub `api.getmoshi.app` (WS, RPC by `hostId`) and Osewa (QUIC/WS) | optional sealed payloads | `moshi-hook pair --token`, QR from `host setup` (expires); Osewa enrolled over SSH first | key whitelist over relay (`Escape`, `Enter` only) |
| herdrup guests | `guest.herdrup.app` (Durable Object) | Noise_IK | short invite links, revocable, audited | allow-list: watch, scrollback, labelled prompts, answer menus, menu keys only while a menu is up; one agent |
| herdrup pair | none (Tailscale/LAN TCP) | SSH | QR with one-time 32-byte token | phone key appended to `authorized_keys` **without restriction** (full shell; do not copy) |

Takeaways: a 32-byte one-time code in a QR/link is the norm; the code must bootstrap a **long-lived
device key**, not be the credential itself (Alma reuses the code forever, so revoking = re-pairing
everyone); guests need a scope narrower than the owner's; the relay must not be able to read traffic.

## 3. Topology

```
agentd-desktop ──wss──►┐                  ┌◄──wss── agentd daemon (host H)
  (device key D)       │   agentd-relay   │          (host key K_H, outbound only)
                       └── route(H) ──────┘
     Noise IK tunnel D ⇄ K_H end to end; the relay forwards opaque frames
       └─ stream mux inside the tunnel; each stream = one daemon socket connection
          (newline JSON ops, attach frames, subscribe events: today's wire protocol unchanged)
```

- **Host link**: the daemon keeps one control connection to the relay (`[relay] url`), registered under
  its **route id** = `base32(SHA-256(K_H.pub))[:26]`. It proves ownership of `K_H` by signing a relay
  challenge. Reconnect with backoff (1 s → 60 s, jitter). Outbound only: the daemon still opens no
  listening port.
- **Client tunnel**: the client opens a connection to the relay naming the route id; the relay pairs it
  with the host link (a new logical channel on the host's connection, or a fresh host data connection
  requested over the control connection; see decision 3). The relay answers `host_offline` at once if
  no host link exists.
- **Inside the tunnel**: a minimal stream multiplexer (open / data / close / window update, per-stream
  credit like the hc layer). Each stream behaves as a `net.Conn`, so the desktop wraps it with
  `client.NewConn(conn, nil)` exactly like an SSH streamlocal channel, and the daemon serves it with
  `handleConn` plus a preset identity (§5). One tunnel per client per host; ops keep using one stream
  each, streams are cheap (no extra handshake).

## 4. Keys, pairing and invitations

### Keys

- Host: `K_H` (X25519 for Noise + Ed25519 for relay auth), `$STATE/relay/host_key` (0600, dir 0700).
  Its public half is the host's identity for clients; changing it forces re-pairing (like an SSH host key).
- Device: `K_D` (X25519), generated by the client on first pairing, kept in the client's state dir
  (desktop: `relay_key`, 0600). Never leaves the device.
- Paired devices on the host: `$STATE/relay/devices.json` (0600, flock): `{id, name, platform,
  pubkey, scope, sessions[], created_at, expires_at?, last_seen, paired_via: invite|cli, kind: owner|guest}`.
  No bearer secrets are stored at all: authentication is the Noise static key.

### Invitation (owner device)

```
host$ agentd relay invite [--name Pixel] [--scope operate] [--sessions 'claude@webapp*'] [--ttl 10m] [--no-approve]
```

- Humans only, and refused when the caller is inside a session (ancestry), so a prompt-injected agent
  cannot mint itself remote access.
- Generates a 32-byte one-time code (TTL default 10 min, max 60; at most 3 live). Prints a terminal QR
  and a link: `agentd://relay?v=1&u=<relay url>&r=<route id>&k=<K_H.pub b64url>&c=<code b64url>&h=<label>`.
- The client verifies `r == hash(k)` (a tampered link pointing at another host fails), opens a tunnel with
  **Noise `IKpsk2`** (responder static = `K_H.pub` from the link, psk = HKDF(code)), sends
  `{name, platform}` and its static key. The relay sees neither code nor keys.
- Host side: the waiting `invite` command asks `Approve "Pixel" (android) as operate? [y/N]` (default no;
  `--no-approve` for scripts), then stores the device key with the invited scope/sessions and burns the
  code. Same limits as `agentd serve pair`: single use, 5 failed handshakes burn the code, pairing lockout
  after 20 failures in 10 minutes.
- Afterwards the device connects with plain **Noise `IK`** (its key + pinned `K_H`): no code, no token.

### Guest invitation (share one agent with someone else)

```
host$ agentd relay invite --guest --sessions codex@webapp [--scope operate] [--expires 24h]
```

Same flow, `kind: guest`: absolute expiry (default 24 h, max 30 d), exactly the listed sessions (no globs
across projects unless given), scope at most `operate`, never `admin`, no mailbox access to the owner's
`human:` mailbox. This is herdrup's guest model on agentd's permission table (§5).

### Management and revocation

`agentd relay devices [list | revoke <id|name> | rename | scope <id> <scope>]`. Revoke = the daemon closes
that device's open tunnels at once and refuses its key from then on. Downgrades apply live; an upgrade
requires a new invite (physical presence at the host). `agentd relay status` shows link state, relay
URL, route id and connected devices.

## 5. Permissions (enforced by the daemon)

A relay peer is a new identity class, `device:<id>`, never `human:<user>`. Today several ops do not check
identity at all (`run`, `kill`, `rm`, `attach`, `dump`, `type`, `shutdown`), because every local caller is
the same uid. A relay stream therefore goes through an **op gate before `dispatch`**: deny by default,
an explicit allow-list per scope, plus a session filter.

| Op | `view` | `operate` | `admin` | notes |
|---|---|---|---|---|
| `ping`, `whoami`, `info` (no `env_base`, no alias dirs below `admin`) | ✓ | ✓ | ✓ | |
| `ls`, `view`, `turns`, `subscribe` | ✓ | ✓ | ✓ | filtered to allowed sessions; events of other sessions and `doc.changed` dropped |
| `attach observe` | ✓ | ✓ | ✓ | |
| `dump` | ✓ | ✓ | ✓ | allowed sessions only |
| `attach` (interactive), `act`, `view_ack` | | ✓ | ✓ | `act` keeps all its guards |
| mailbox `send`/`inbox`/`read`/`reply` as `human:<user>` | | ✓ owner | ✓ | guests: none |
| `run` (alias/target + harness from a profile) | | | ✓ | `cmd`/`env`/`env_base` from the device: never (decision 5) |
| `kill`, `rm`, `label`, `doc_get`/`doc_set` | | | ✓ | |
| `type` (raw), `purge`, `shutdown`, `hc_listener`, `claim`, `queue` | ✗ | ✗ | ✗ | never over the relay |

- **Session filter**: `sessions[]` globs on names (and optionally `project:<alias>`), checked on every op
  that names a session, on `ls`/`subscribe` results, and on `run` (the new name must match). Empty = all.
- **Scope = risk**: `operate` can type into agents that run shell commands, so it is shell-equivalent on
  the host, like the gateway's `write`. The UI and the invite prompt say so.
- **Mail identity**: an owner device sends as `human:<user>` (it is the owner); the audit log records the
  device id. Guests get no mailbox ops in v1.
- **Audit**: `$STATE/relay/audit.log` (JSONL 0600, capped, one rotation): pair, revoke, connect,
  disconnect, run, act, kill, rm, send, view_ack with device id; never prompt text or bodies (as the
  gateway).
- `[relay] max_scope` (default `operate`) caps what any invite may grant on this host.

## 6. Relay server (`cmd/agentd-relay`)

- Separate binary, `CGO_ENABLED=0`, imports nothing from `daemon`/`session`/`desktopui`; shares only the
  wire framing package (`internal/relaywire`).
- Listens HTTPS/WSS (TLS files, or ACME via `golang.org/x/crypto/acme/autocert`). Endpoints:
  `GET /v1/host` (host link upgrade), `GET /v1/connect?r=<route>` (client upgrade), `GET /healthz`.
- **Host admission**: open registration with per-key quotas, or a relay `join_token` (env) required to
  register a route (private relays; recommended default). Hosts authenticate by signing a challenge with
  `K_H`; a route id is bound to the first key that proves it (it is a hash of the key, so no squatting).
- **Client admission**: none at the relay level (clients are authenticated end to end by the host).
  Abuse controls: pre-handshake rate limits per IP and per route, max tunnels per route (64), max
  pending handshakes, idle timeout, per-tunnel bandwidth cap, frame size cap (64 KiB).
- Stateless except live routes in memory; nothing written to disk except its TLS material. Logs carry
  route ids and byte counts, never payloads.
- What a relay operator learns: which route ids are online, client IPs, timing and volume. Not session
  names, screens, prompts or keys.

## 7. Daemon side

- Config `[relay]` (`internal/config/relay.go`): `enabled` (false), `url` (`wss://…`), `label` (host label
  offered to clients), `join_token_env`, `max_scope`, `max_devices` (16).
- Package `internal/relaylink` (daemon-owned, outbound only): host link, Noise responder, stream mux,
  device store. Each accepted stream is handed to `Server.handleConn` with a **preset caller**
  (`caller{id: "device:<id>", device: true, scope, sessions}`), skipping `peerOf` and ancestry. The op
  gate (§5) runs before `dispatch`, `handleAttach` and `handleSubscribe`.
- Started from `Serve` when enabled, stopped first in `Shutdown` (tunnels get `bye`). Op `relay`
  `{action: status|invite|devices|revoke}` humans only (refused inside sessions); the CLI uses it.

## 8. Client side (agentd-desktop)

- `backend.Host` gains a transport: `ssh` (today) or `relay {url, route, host_key, label}`; `hosts.json`
  stores it; the device key lives in `remote.Dir()/relay_key`.
- "Add host" offers: SSH (today) | Relay invite (paste the link or scan/drop the QR image).
- `core` dials either an SSH streamlocal channel or a relay stream, then `client.NewConn(conn, nil)`;
  the rest of `core` (ls, subscribe, view, act, attach) is unchanged. Ops the device's scope forbids come
  back as `forbidden`; `whoami` returns `{id: "device:…", scope, sessions}` so the UI hides actions it
  cannot do (no Terminar / New session without `admin`).
- No zellij/tmux/plain shells over the relay: those need a shell on the host (SSH only).

## 9. Threats

| Threat | Mitigation |
|---|---|
| Malicious or compromised relay | E2E Noise with the host key pinned from the invite; relay cannot read, inject or replay (Noise nonces); it can only drop or delay |
| Leaked invite link | One-time, short TTL, host approval by default; once used it is worthless |
| Stolen device | `relay devices revoke` closes live tunnels; guests expire; optional inactivity expiry (90 d) |
| Agent tries to grant itself remote access | `relay invite` / op `relay` refused from sessions (ancestry + token) |
| Relay peer reaching ops never meant for remote | deny-by-default op gate, `type`/`shutdown`/`purge`/`hc_listener` never allowed |
| Host key loss / rotation | re-pair (clients show "host key changed" like SSH, never silent re-trust) |
| DoS through the relay | relay rate limits; the daemon caps tunnels per device (4) and streams per tunnel (64) |

## 10. Relation to other work

- [[design/cross-host-relay]] is **mail bridging through a client** (agents on different hosts messaging
  each other). It is independent: it can use SSH or relay transports. Suggest renaming it "mail bridge"
  to avoid two meanings of "relay".
- The HTTP gateway stays frozen; this replaces it as the remote path for clients that cannot SSH.
  `apitoken`'s pairing rules (limits, lockout, approval prompt) are reused as a spec, not as code
  (`apitoken` is tied to `httpapi` types).
- Herdr clients (Whip, 0cv relay, Alma, Moshi) do not speak this; out of scope.

## 11. Phases (each testable on its own)

1. `internal/relaywire`: frame codec, stream mux over any `io.ReadWriteCloser` (credit, close, limits). Pure, `-race` tests.
2. Noise layer + keys (IK, IKpsk2), invite link format and parser. Tests with fixed vectors.
3. `cmd/agentd-relay`: routing, host auth, limits; tests with in-process host and client.
4. Daemon: `[relay]` config, `relaylink`, device store, preset caller + op gate, session filter on `ls`/`subscribe`/events; op `relay`, CLI `agentd relay invite|devices|status`, audit. Tests with the fake agent through an in-process relay.
5. Desktop: relay transport in `core`, Add host by invite, scope-aware UI; headless tests on the fake backend.
6. Guests (`--guest`), inactivity expiry, docs (README, AGENTS.md contracts and pinned deps).

## 12. Open decisions

1. **Where the link runs**: inside the daemon (recommended: identity and session filtering need the daemon,
   and it is outbound only) or a separate `agentd relay connect` process that dials the socket as `human`
   and enforces scopes itself, like the gateway (keeps the daemon free of network code, duplicates filtering).
2. **Dependencies**: WebSocket (`github.com/coder/websocket`, needed for a future browser/mobile client) vs.
   raw TLS + our framing; Noise (`github.com/flynn/noise`) vs. hand-written over `x/crypto`. Both need the
   pinned-deps list updated.
3. **Relay pairing of streams**: one host connection multiplexing every tunnel (simpler relay, head-of-line
   risk) vs. a fresh host data connection per tunnel requested over the control link (recommended).
4. **Scopes**: `view / operate / admin` as above, or reuse the gateway names `read / write / admin`.
5. `run` over the relay: `admin` with profile harnesses only (recommended), or never.
6. Host admission on the relay: `join_token` required by default (recommended) or open registration.
7. Do we host a public relay, or only ship the binary for self-hosting?
8. Mobile: no agentd mobile client exists now; is desktop-first acceptable?
